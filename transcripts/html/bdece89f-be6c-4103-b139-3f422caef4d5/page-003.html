# Modal Volumes: Key Technical Details

## (1) Consistency Model

**Write Visibility & Commits:**
- "Unlike a normal filesystem, you need to explicitly reload the Volume to see changes made since it was first mounted."
- `.commit()` is required for persistence: "any Volume changes made within a container need to be committed for those changes to become visible outside the current container."
- `.reload()` fetches latest changes from other containers.

**Default Version:**
The document does not specify which version is default for newly created volumes.

**V1 vs V2 Differences:**

| Aspect | V1 | V2 |
|--------|----|----|
| File limit | 500,000 inodes; recommend <50,000 | Unbounded (262,144 per directory max) |
| Concurrent writers | Recommend ≤5 concurrent commits | "hundreds of containers" without degradation |
| Reload/commit speed | Slower | Faster |
| Commit method | `.commit()` only | `.commit()` or `sync /path` command |

## Commit and Reload Semantics

The simplest rule is: writers commit, readers reload. A training job writes a checkpoint, commits it, and then a later job can reload the Volume and find that checkpoint.

## Important SQLite Guidance

Last write wins in case of concurrent modification of the same file — any data the last writer didn't have when committing changes will be lost! Volumes are typically not a good fit for use cases where you need to make concurrent modifications to the same file (nor is distributed file locking supported).

## Reload Constraints

Volumes can only be reloaded if there are no open files for the volume - attempting to reload with open files will result in an error.

## Background and Explicit Commits

Writes made inside a container are not guaranteed to be visible elsewhere until they are committed. Modal supports explicit commit() calls, and its documentation also describes background commits that run every few seconds during function execution, plus a final commit when the container shuts down.

## For Single Writer SQLite Pattern

The search results reference modal-mosql, which appears to be a tool for managing SQLite with Modal Volumes using explicit durability boundaries where each committed transaction is published either by committing the volume the database lives on, or by appending an LTX record to an ordered log.
