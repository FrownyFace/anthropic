## 1. What it is

Faultline is a mini agent harness with a browser view. A Claude agent runs real shell commands (read
files, edit code, run tests) inside an isolated Modal Sandbox while the environment deliberately injects
failures at the tool boundary: a missing file, a denied write, a write that lands but whose acknowledgement

graded score. Runs are grouped into conversations that belong to an anonymous browser identity and are
persisted in SQLite on a Modal Volume, so a reviewer can close the tab, come back, and re-read the
transcript.

### 2.9 Persistence: SQLite on a Modal Volume (harness `Store`)

Full write-up, DDL and decision log: `ARCHITECTURE.md` §4. This section is the plan-level summary.

**What is persisted.** The browser's anonymous identity, its conversations, every run, the append-only
event log of each run, and a transcript projection (messages → content blocks, plus one `llm_calls`
row per `messages.create`). Episode state (fault plan, ledger) stays in sandbox-env's
`modal.Dict "faultline-episodes"` — ephemeral by design and never readable by the harness.

**Today's code (17:41 EDT).** `harness/store.py` is `RunStore` over the Modal Dict `faultline-runs`:
one whole `RunRecord` per run, re-`put` on every event, plus a 200-entry index. `api.py` has
`/health /scenarios POST /runs GET /runs GET /runs/{id} GET /runs/{id}/events`, CORS `allow_headers=["*"]`.
Migration: keep the `RunStore` interface (`get / create / list_runs`) as a thin client over the new
`Store` class so `loop.py` and `api.py` change minimally; add `append_events` so the loop stops
re-persisting whole records; drop the Dict.

**Modal facts that shape the design** (docs + `modal==1.5.5`, verified 2026-09-12):
- Volumes are "write-once, read-many"; writes become visible to other containers only after a commit
  (background commits every few seconds, plus explicit `.commit()`); other readers must `.reload()`.
- "Last write wins in case of concurrent modification of the same file"; no distributed file locking.
- Modal's own SQLite example (Datasette) builds the DB on local disk, copies it onto the Volume, commits.
- Volume v2 needs explicit `version=2`; the 1.5.5 CLI marks it experimental → v1.

**Decision — one writer, hot copy on local disk, consistent snapshots on the Volume.**
- `Store` = Modal class, `max_containers=1` (single writer; the only process that ever opens the DB),
  `min_containers=1` (no cold start per SSE poll). `@modal.concurrent(max_inputs=32)` + a
  `threading.Lock` around the connection; ops are sub-millisecond on local disk.
- DB at `/tmp/faultline.sqlite3` (`journal_mode=WAL`, `synchronous=NORMAL`, `foreign_keys=ON`) —
  plain SQLite semantics, no FUSE locking/mmap questions.
- Checkpoint = `VACUUM INTO '/data/faultline.sqlite3.tmp'` → `os.replace` → `vol.commit()`. Always a
  complete, consistent single file (a background commit can never capture a half-written DB).
  Triggered after every `run.finished`, every 15 s while dirty, and in `@modal.exit`.
  `@modal.enter` restores `/data/faultline.sqlite3 → /tmp` (or creates an empty DB) and runs
  migrations (`PRAGMA user_version`, `harness/migrations/000N_*.sql`).
- Loss window: ≤ the last 15 s of an *in-flight* run if the Store container dies. Completed runs
  self-heal: `append_events` is idempotent on `(run_id, seq)` and `run_episode` re-sends its full
  in-memory event list at `run.finished`.
- Nobody else touches the file. `api` and `run_episode` call `Store().<method>.remote(...)`; reads need
  no `reload()` because the reader *is* the writer.
- Accepted limit: one Store container, full-file snapshot per checkpoint. Past ~100 MB move to
  incremental shipping (Litestream-style / `modal-mosql`) or Postgres. Not a take-home problem.

102	## 4. Persistence layer: SQLite on a Modal Volume
103	
104	### 4.1 Requirements
105	
106	Persist, per anonymous browser user: conversations, runs, the full event log of each run, and the LLM
107	turns including tool calls and their results, in a shape that can (a) render a chat transcript without
108	replaying events, and (b) rebuild the exact `messages=[…]` array the model saw at each step. Survive page
109	reloads, browser restarts, and redeploys. No external database service.
110	
111	### 4.2 Modal facts that constrain the design
112	
113	- Volumes are "write-once, read-many". Writes are visible to other containers only after a commit
114	  (Modal background-commits every few seconds and on container shutdown; `.commit()` forces one).
115	  Other containers must `.reload()` to see committed changes, and reload fails while files are open.
116	- "Last write wins in case of concurrent modification of the same file" — there is no distributed file
117	  locking. Concurrent writers to one SQLite file would corrupt it.
118	- The mount is a FUSE filesystem. SQLite's WAL mode relies on a shared-memory-mapped `-shm` file and
119	  POSIX advisory locks; their behaviour on the mount is undocumented. A background commit is not a
120	  point-in-time snapshot across files, so a live DB + its journal could be captured inconsistently.
121	- Modal's own SQLite example (the Datasette cron) builds the database on local disk, copies it onto the
122	  Volume, and commits. That is the pattern to copy.
123	- Volume v2 must be requested explicitly (`version=2`); the 1.5.5 CLI still marks it experimental. v1 is
124	  fine for one file.
125	
126	### 4.3 Design: one writer, hot copy on local disk, consistent snapshots on the Volume
127	
128	```
129	 api ──.remote()──▶ ┌───────────────── Store (1 container) ─────────────────┐
130	 run_episode ──────▶│ /tmp/faultline.sqlite3   WAL, synchronous=NORMAL, FK on │
131	                    │   ▲ restore on @modal.enter        checkpoint ▼         │
132	                    │ /data/faultline.sqlite3  ◀── VACUUM INTO .tmp + os.replace + vol.commit()
133	                    └────────────────────────────────────────────────────────┘
134	                                   Modal Volume "faultline-db" (v1)
135	```
136	
137	- **Single writer.** `Store` is a Modal class with `max_containers=1`. It is the only process that ever
138	  opens the database, so SQLite's locking assumptions hold trivially and nobody needs `reload()` — the
139	  reader *is* the writer. `min_containers=1` keeps it warm (an SSE poll must not pay a cold start plus a
140	  restore). `@modal.concurrent(max_inputs=32)` lets many `api` polls and one run's appends interleave; a
141	  `threading.Lock` serialises access to the single `sqlite3` connection (ops are sub-millisecond).
142	- **Hot copy on local disk.** The live file is `/tmp/faultline.sqlite3` on the container's own disk with
143	  ordinary SQLite settings (`journal_mode=WAL`, `synchronous=NORMAL`, `foreign_keys=ON`,
144	  `busy_timeout=5000`). No FUSE questions.
145	- **Checkpoint.** `VACUUM INTO '/data/faultline.sqlite3.tmp'` writes a complete, consistent, single-file
146	  copy; `os.replace()` renames it over `/data/faultline.sqlite3`; `vol.commit()` publishes it. Because
147	  only complete files are ever renamed into place, a background commit can never capture a half-written
148	  database. Triggers: after every `run.finished`, every 15 s while there are unsaved writes, and in
149	  `@modal.exit`. A `checkpoint_now` local entrypoint forces one for evidence/export.
150	- **Restore.** `@modal.enter` copies `/data/faultline.sqlite3` → `/tmp` if present (else creates an empty
151	  DB), then applies migrations: `PRAGMA user_version` gates `harness/migrations/000N_*.sql`, applied in
152	  order inside one transaction each.
153	- **Durability model.** Completed runs are durable as soon as their post-`run.finished` checkpoint commits
154	  (seconds). If the Store container dies mid-run, at most the last ≤15 s of that run's events are lost
155	  from the Volume — and they are not lost from the system: `append_events` is idempotent on
156	  `(run_id, seq)` (`INSERT OR IGNORE`), and `run_episode` re-sends its complete in-memory event list at
157	  `run.finished`, which back-fills any gap. A redeploy briefly overlaps old and new Store containers; the
158	  same idempotent re-send covers the overlap for runs that finish, and the ≤15 s window is documented for
159	  runs that don't.
160	- **Ids.** `<prefix>_<hex ms timestamp><12 hex random>` (sortable, no extra dependency): `c_`, `r_`, `m_`,
161	  `b_`, `l_`. User ids are minted by the browser as `u_<uuid4>`.
162	- **Migration from the current code.** `harness/store.py` today is `RunStore` over the Modal Dict
163	  `faultline-runs` (one whole `RunRecord` per run, re-put on every event, 200-entry index). The
164	  `RunStore` interface (`get / create / list_runs`) is kept as a thin client over `Store` so `loop.py`
165	  and `api.py` change minimally; the loop switches from whole-record puts to `append_events` per step
166	  plus a full idempotent re-send at `run.finished`; the Dict is dropped.
167	- **Ops.** `modal volume get faultline-db faultline.sqlite3 runs/` yields a consistent file for local
168	  `sqlite3` inspection and for the evidence folder. Retention: none for the take-home (a `DELETE`
169	  archives; nothing is hard-deleted).
170	- **Known limits (accepted).** One Store container; full-file snapshot per checkpoint. Comfortable to
171	  hundreds of MB; past that, ship incrementally (Litestream-style, or `modal-mosql`) or move to Postgres.
172	  A single-writer actor is also a throughput ceiling (thousands of events/s — orders of magnitude above
173	  need).

291	### 4.5 Event → transcript projection
292	
293	Performed inside `Store.append_events`, per event, in the transaction that inserts the event row:
294	
295	| Event | Effect |
296	|---|---|
297	| `run.started` | `runs.status='running'`, `started_at`; `conversations.updated_at` |
298	| `episode.reset` | `runs.episode_id`; user message (`step NULL`) with one `text` block = `task_prompt` |
299	| `turn.thinking`, `turn.text`, `tool.call` (same `step`) | one assistant message for that step (created on first block); blocks appended in event order: `thinking`, `text`, `tool_use{tool_name, tool_use_id, input_json}` |
300	| `tool.result` (same `step`) | one user message for that step (Anthropic requires tool results in a user turn); `tool_result{tool_use_id, text=output, is_error, exit_code, duration_ms, fault_json}` |
301	| `llm.call` | `llm_calls` row; running totals into `runs.input_tokens/output_tokens` |
302	| `episode.evaluated` | `runs.score`, `runs.evaluation_json`; assistant message with the submit summary |
303	| `run.finished` | `runs.status`, `finished_at`, `error`, final usage; `conversations.updated_at`; marks the DB dirty for checkpoint |
304	| `fault.fired`, `workspace.diff`, `log` | event row only; the UI reads them from the event log |
305	
306	Rebuilding the model's view of step *n*: take the conversation's messages for the run with `seq` up to
307	the assistant message of step *n − 1* plus its tool-result message, expand blocks in `seq` order, map
308	`text/thinking/tool_use/tool_result` one-to-one onto Anthropic content blocks. The UI instead groups each
309	`tool_result` under its `tool_use` by `tool_use_id` and renders it as a tool chip inside the assistant turn.

348	## 6. Identity
349	
350	- **Minting.** `src/lib/identity.ts`: read `localStorage["faultline.user_id"]`, else the `faultline_uid`
351	  cookie, else mint `"u_" + crypto.randomUUID()`; write back to both. Cookie attributes:
352	  `SameSite=Lax; Secure; Max-Age=31536000; Path=/`. Not `HttpOnly` (JS writes it). All storage access is
353	  wrapped in try/catch; a browser that blocks storage still works for the session with an in-memory id.
354	- **Transport.** The harness API lives on a different origin from the SPA, so cookies are never sent to
355	  it. The id travels as `X-Faultline-User` on every request; the harness CORS config allows that header.
356	- **Why both stores.** localStorage is the primary (no size/attribute quirks, not sent anywhere);
357	  the cookie only exists so the id survives a "clear site data → local storage" that leaves cookies.
358	- **Threat model.** This is scoping, not authentication (explicit non-goal). Ids are 122-bit random and
359	  never listed, so they are unguessable in practice, but anyone holding one can read that browser's
360	  transcripts. Nothing sensitive is stored: scenarios are bundled, the workspace is a fixture, and the
361	  provider key never leaves `run_episode`. `POST …/runs` is rate-limited per id.

448	## 9. Decision log
449	
450	| # | Decision | Alternatives considered | Why |
451	|---|---|---|---|
452	| 1 | Three Modal apps with a strict secret boundary | one app | harness swappable, environment gradeable without trusting the agent, static UI; the provider key exists in exactly one function |
453	| 2 | Faults injected at the tool boundary, not inside the shell | `chmod`, deleting files live, network faults | deterministic, seedable, invisible to the agent, gradeable from a ledger; ack-lost is only expressible at the boundary |
454	| 3 | `spawn` + event log + reconnecting SSE | run the loop inside the request | Modal web requests cap at 150 s |
455	| 4 | Persistence = SQLite on a Modal Volume | Modal Dict only; hosted Postgres; Modal Dict as hot path + SQLite archive | user asked for it; zero external services; a single file is trivial to export as evidence |
456	| 5 | Single-writer `Store` actor (`max_containers=1`) | every function opens the DB on the Volume; per-run DB files | Volumes have no distributed locking and last-write-wins; one process owning the file removes every consistency question |
457	| 6 | Hot DB on local disk, `VACUUM INTO` snapshots renamed atomically onto the Volume | run SQLite directly on the FUSE mount | WAL/locking on FUSE is undocumented, and background commits are not multi-file snapshots; Modal's own example copies-then-commits |
458	| 7 | Volume v1 | v2 | v2 needs an explicit flag and is marked experimental in the 1.5.5 CLI; no benefit for one file |
459	| 8 | `events` as source of truth + `messages`/`blocks`/`llm_calls` projections | events only; projections only | replay/SSE need the log; the UI and "what did the model see" need the message shape; projections are a cheap same-transaction write and a listed scope cut |
460	| 9 | Identity via `X-Faultline-User` header, minted in the browser, mirrored to a cookie | cookie-only; server-minted id | the API is cross-origin so cookies never reach it; localStorage is the reliable store; the cookie is a backup |
461	| 10 | Beautiful UI by copy-paste with lucide/shadcn substitutions | Vercel AI Elements (a real registry); shadcn only | matches the requested look; MIT; the private deps are small and swappable; scope cut #4 if it drags |
