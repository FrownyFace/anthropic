Why the landing reads worse than the README

The README does three things in its first screen: names the thing in one sentence, says what happens in one paragraph, and gives numbered steps. The landing does none of them.

  • No definition. The headline is a riddle ("What should the agent survive today?"). The page never says what Faultline is.
  • Mechanism before meaning. The five bullets use insider nouns: "tool boundary", "acknowledgement is lost", "grader outside the agent's reach", "workspace diff", "backend". The README says the same things as "a file that isn't there, a write that is denied, a write that succeeds but whose response times out".
  • Instructions are the smallest text on the page. An 11 px hint under the composer and a 12 px line above the table are the only "how to use it".
  • Bullet 2 is false. "Injects one failure at the tool boundary" is wrong for gauntlet (three), missing-config (a real deletion at reset) and worker-crash (a real process kill). The review doc already flagged this at web-review-findings.md §7.3.
  • Code identifiers as prose. The table shows missing_file, ack_lost, EACCES, EHARNESS to a reader who has not opened the repo.
  • One concept, many words. "Max turns" in the table but "steps" everywhere else. "Failure injected" heads a column that holds a real crash. Badge says "simulated", header says "injected", story bar says "intercepted". "Episode" and "run" are used interchangeably.
  • The point is missing. Nothing on the page states the experiment the project exists for: the write that landed but whose reply timed out, and checking versus retrying blind.

Proposed landing copy

Headline and intro, replacing the H1 and the five bullets:

An agent harness where the environment fights back.

A Claude agent edits a small Python repo with real shell commands inside an isolated sandbox. Faultline breaks things on purpose: a file goes missing, a write is refused, or a write lands but its reply times out. Retry that last one without looking and you can write the change twice. You watch every command, see whether the agent recovers, and get a graded score.

Three numbered steps at body size, mirroring the README's "Try it in 60 seconds":

  1. Pick a scenario. Press Run on a row below, or type / in the box to choose one and edit its task first.
  2. Watch the run. Every command, its output, the failure when it hits, and the file changes. Live runs take one to two minutes. No API quota? Press Replay instead: a recorded run, no server needed.
  3. Read the score. Hidden tests are worth 60 points and recovery checks 40, so finishing the task is not enough.

Table headers become "Scenario · What goes wrong · Step budget · Failure · Run · Replay". Badges become words with the origin the transcript already uses: "staged: missing file", "simulated: lost ack", "real: worker crash". The checks tooltip switches to the plain-English text that already exists in src/lib/checks.ts instead of the raw grader strings. Composer hints drop "episode" and "harness URL" for "connecting…", "live runs are offline — Replay still works". The seed chip either gets a tooltip or goes away: PLAN §3.1 says the seed is stored but unused, so for a reviewer it is a control that does nothing.

What is not the web's to change, and what applying touches

  • Scenario descriptions are the longest text on the page and come from the sandbox-env JSON catalogue. I drafted a shorter set with one shape per row (what goes wrong, then what a careful agent does, no error codes). That is the sandbox-env owner's change, and PLAN §2.6 mirrors them.

  • Glossary for the rest of the app. One word per concept: step not turn, run not episode, simulated / staged / real for origin, "the reply timed out" instead of "acknowledgement is lost" in prose. The doc lists the secondary strings in the story bar, status strip and provisioning state.

Yes, but keep it to one small line plus one short column, written in the assignment's own words so the reviewer sees the mapping without reading a pitch.

The PDF describes Theme 3 as "handle failure, concurrency, and scale", and offers three shapes: "a developer tool that solves a real workflow pain point", "a distributed primitive that handles failure gracefully", or "infrastructure that degrades predictably under stress". Faultline hits the first and third directly, and the worker-crash proof is the strongest "handles failure gracefully" evidence in the repo. That is what the page should say, and it currently says none of it. The README does, in its one blockquote line.

Proposed additions to the landing, nothing else moves:

  1. A kicker above the headline, small and muted, like the README's line:

    Anthropic Platform SWE take-home · Theme 3: Systems & Reliability, with a Theme 4 Evaluation twist

  2. A third column, "Why Theme 3", next to "What goes wrong" and "Try it in 60 seconds", one bullet per phrase the theme uses:

  3. A real workflow pain point. Tool-using agents fail at the tool boundary in production. This is a developer tool for reproducing those failures and watching the recovery.
  4. Handles failure gracefully. Kill the harness worker mid-write and a fresh worker resumes the same run from the saved event log. That is the worker-crash scenario.
  5. Degrades predictably. Every failure is labelled real, staged or simulated, so nothing is blamed on the wrong layer, and a run that could not be graded is never shown as a pass.
  6. The Theme 4 twist. Recovery is graded by hidden tests and checks on the execution ledger, not eyeballed.

Two things to keep honest in that copy. The worker-crash claim rests on the saved live proof in the README (worker generation 2, score 100), which is fine to state, but the bundled replay for it does not exist yet, so a reviewer without quota can only read about it.
